A proposed continuity program

Pair reviewed ACCESS / NAIRR compute with institution-funded application hosting, databases, durable storage, and Libraries stewardship. This is a proposed pilot, not an existing service, approved award, migration, or account change.

  1. Inventory the whole course stack

    For two pilot courses, map compute, live app, database, object files, Git, and archival deposits. Record each owner, account, region, quota, expiry and course requirement. Distinguish public teaching examples from private submissions and research materials.

    Instructor + college IT + Libraries · 12–10 weeks before term

  2. Choose a bounded free route and a funded fallback

    Use static hosting where no backend is needed; Neon for small Postgres coursework, Workers/D1 for lightweight SQLite-style apps, or Supabase when integrated auth is part of the exercise. Provision through supported institutional services when available. For persistent multi-user courses, fund managed app/database hosting or an IT-supported environment through the assessment and export period.

    College IT + course lead · 10–8 weeks before term

  3. Separate compute awards from service operations

    Request reviewed ACCESS capacity and eligible NAIRR Classroom pilots for instruction and analysis. Separately commit the budget and operator for databases, application availability, durable object storage, identity, backups and renewal. Do not assume a research allocation supports permanent public hosting or preservation; check the awarded resource’s rules.

    College leadership + IT + allocation lead · before committing the course

  4. Make the course portable and recoverable

    Keep versioned app source, schema migrations, dependency definitions and synthetic seed data. Export the database and uploaded files independently to institution-approved storage; include metadata, licenses, checksums and necessary access configuration. Protect credentials and define retention with the appropriate institutional owners. A Git mirror or provider snapshot alone does not preserve this whole stack.

    Named service operator · automated backups with failure alerts

  5. Rehearse real class load and a second-host restore

    Test simultaneous class use, cold starts, deployment/egress/query quotas, inactivity and expiration handling. Restore an app, database and sample file set onto a second host; verify private access, schema, queries and grading links. Proposed pilot recovery targets remain at most 24 hours of data loss and one business day to restore; measure them before promising them.

    Operator + instructor · 4–2 weeks before term and after major changes

  6. Close and preserve the course deliberately

    Offer portable student exports; retain assessment records under approved policy. Coordinate suitable public scholarly deposits with Campus Repository, ReDATA or a disciplinary repository, including metadata and persistent identifiers. Budget stewardship beyond the award period. Recheck vendor terms and test recovery before the next cohort; move active OSF Projects before the announced freeze.

    Instructor + Libraries + IT · end of term and annual review

Pilot two courses before scaling. Readiness requires a named operator, a funded service period, correct access controls, a tested cross-host restore, and a usable export at the end of term. Allocation expiry and vendor policy changes must have a rehearsed fallback.
